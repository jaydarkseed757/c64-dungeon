## 2b. Copying release files to the C64 Ultimate

```bash
make ultimate-dry
```

```bash
make ultimate
```

- `make ultimate` FTPs the release files to `<USB>/dist/dungeon-master/` on the Ultimate. It asks once before overwriting.
- It uses `tools/ultimate_upload.py`, standard library only, modelled on `../ultimate-dist/ultimate_dist.py`.
- Host: `ULT_HOST`, default `192.168.10.148`. Anonymous FTP unless `ULT_FTP_USER` / `ULT_FTP_PASSWORD` are set.
- The USB root is auto-detected (`/USB1` on the dev unit). Override it with `--usb`.
- Every file is size-checked after upload.
- `python3 tools/ultimate_upload.py --check` only connects and lists the target folder.

Files shipped so far (the `MANIFEST` list in the script):

| Local file | On the Ultimate |
| --- | --- |
| `terminal/build/dm64.prg` | `DM64.PRG` (the AI terminal) |

## 4. C64 Ultimate setup and hardware workflow

Verified on the user's C64 Ultimate: Starlight Edition, firmware 1.1.0, at `192.168.10.148`. The item names were read with `GET /v1/configs/...`.

| Category (REST) / menu | Item | Value for DM64 | User's normal setting |
| --- | --- | --- | --- |
| C64 and Cartridge Settings | RAM Expansion Unit | Enabled | Enabled |
| C64 and Cartridge Settings | REU Size | 16 MB | 16 MB |
| U64 Specific Settings | Turbo Control | C64U Turbo Registers (64 MHz) | **Off** |
| C64 and Cartridge Settings | Command Interface | Enabled (optional: lets DM64.PRG load the model from USB) | **Disabled** |
| C64 and Cartridge Settings | REU Preload | optional | Disabled |

**Hardware scripts.** Each one resets the C64 through `runners:run_prg`; the REU keeps its contents.

| Command | What it does |
| --- | --- |
| `make hw-check` / `.venv/bin/python tools/hw_check.py --ultimate [--uci [--damage]]` | Engine check: REU, model CRC; with turbo, a generation timing. `--uci --damage` proves file loading through the Command Interface. |
| `make hw-terminal` / `.venv/bin/python tools/terminal_hw.py [--exact] [--prompt T] [--scene F1]` | Runs `DM64.PRG`, types over REST (`machine:writemem` to `$0277`/`$C6`), and reads the answer and screen. `--exact` compares with the reference. |
| `make ultimate` | FTP the release files to `/USB1/dist/dungeon-master/` (asks first) |
| `python3 tools/ult_screenshot.py out.png [--scale 2]` | Screenshot. Uses the VIC video stream if available (needs wired Ethernet), otherwise a text-mode reconstruction from screen and colour RAM read over REST. Read-only; does not reset the C64. |

**Settings policy for automated runs.** Turbo Control and the Command Interface may be changed over REST:

```bash
curl -s -X PUT "http://192.168.10.148/v1/configs/U64%20Specific%20Settings/Turbo%20Control?value=C64U%20Turbo%20Registers"
```

- Change them only for the run, never save to flash, and put the previous value back afterwards (verify with a `GET`).
- Ask before uploading files or changing other settings.
- The REST API needed no password on this unit (checked 2026-11-16).

Record firmware, FPGA and core versions, and the settings used, with every hardware result in `docs/HW_RESULTS.md`.

## 5. VICE usage

```bash
x64sc -pal -reu -reusize 16384 -reuimage models/exported/baseline.d64ai terminal/build/dm64.prg
```

- VICE wants an REU image of exactly the REU size. `tools/vice_harness.py` pads a copy automatically.
- Correctness and cycle counts come from VICE (cycle-exact PAL, 1 MHz).
- VICE has no `$D031` turbo registers and no Command Interface. Speed, turbo and file loading are measured on hardware only.
- **Automation:** `tools/vice_harness.py` uses the binary monitor (TCP). It boots to BASIC READY, injects a PRG, sets PC, runs to a checkpoint, and reads and writes memory and registers.
- **Test hosts:** `engine/tests/test_host.asm` (kernel dispatcher) and `engine/tests/api_host.asm` (public API).
- **Terminal:** `tests/terminal_harness.py`.
- **Game:** `tests/game_harness.py`.
- **Screenshots from VICE:** `tools/ult_screenshot.capture_memory(None, read=...)` renders VICE memory the same way it renders the Ultimate's.

## 6. Engineering workflow

1. Python first: every numeric routine exists in `python/reference_int.py` before it is written in assembly.
2. Write the assembly kernel, then test it in isolation against Python-generated vectors (bit-exact).
3. Integrate. A full-token test compares every intermediate tensor with the reference.
4. Benchmark in VICE (cycles, `make profile`), then on hardware (time, `docs/HW_RESULTS.md`).
5. Optimize only with the correct version kept as a reference. Re-run the bit-exact tests after every optimization.

**Conventions:**

- ACME source uses `!cpu 6510`.
- Engine zero page and fixed addresses come only from `engine/include/memory.inc`; the public interface from `engine/include/ai_api.inc`.
- Every routine header documents inputs, outputs and clobbers.
- Self-modifying code is marked with the patched operand named.
- Out-of-range branches: run ACME through `python3 tools/acme_longbranch.py acme ...`. It rewrites them with unique labels.

**6502 pitfalls hit in this project (check for them in review):**

- `CPX`/`CPY`/`CMP` change the carry flag. Never put them between the bytes of a multi-byte `ADC`/`SBC` chain; count with `DEX`/`DEY` instead.
- `reu_xfer` clobbers `tmp0`–`tmp4`; `round_shift64`/`udiv64` clobber `cnt0`. Never keep a loop counter or value there across those calls.
- RAM is not zero at power-on (VICE fills a pattern). Initialize every flag and parameter-block field: `AI_INIT` sets the parameter block to defaults, and init flags live in the PRG image.
